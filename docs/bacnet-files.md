# Existing BACnet File objects and native JCI application uploads

`BacnetFiles` reads already exposed standard BACnet File objects and saves opaque file evidence locally. It does not generate a CAF, start a backup session, freeze a controller, upload new logic, or convert proprietary application storage. An object/property inventory is also separate from an executable controller application.

## Primary evidence and the native boundary

The manufacturer's [FX-PCV PICS](https://docs.johnsoncontrols.com/bas/r/Facility-Explorer/en-US/FX-PC-Series-Controllers-Protocol-Implementation-Conformance-Statement/Annex-A-Protocol-Implementation-Conformance-Statement-Normative) names PCV1615/1630-family controllers at firmware 6.2. Its [BIBB list](https://docs.johnsoncontrols.com/bas/r/Facility-Explorer/en-US/FX-PC-Series-Controllers-Protocol-Implementation-Conformance-Statement/BACnet-Interoperability-Building-Blocks-BIBBs-Annex-K) includes DM-BR-B backup/restore, and its [Device properties](https://docs.johnsoncontrols.com/bas/r/Facility-Explorer/en-US/FX-PC-Series-Controllers-Protocol-Implementation-Conformance-Statement/Standard-Object-Types-Supported/Device) include Configuration_Files (154) and Backup_Fail_Timeout (153). The separate [VMA1615/1630 PICS](https://docs.johnsoncontrols.com/bas/r/Metasys/en-US/Field-Equipment-Controllers-Protocol-Implementation-Conformance-Statement/Annex-A-Protocol-Implementation-Conformance-Statement-Normative) documents the same firmware generation. Its [File definition](https://docs.johnsoncontrols.com/bas/r/Metasys/en-US/Field-Equipment-Controllers-Protocol-Implementation-Conformance-Statement/Standard-Object-Types-Supported/File?contentId=OXNOTVYw3~V9aPv2sSXVSg) describes non-creatable/non-deletable File objects. None of these pages maps a File instance to a CAF or supplies a proprietary application decoder.

The primary [ASHRAE 135.1-2011 Addendum m](https://resourcecenter.ashrae.org/File%20Library/Technical%20Resources/Standards%20and%20Guidelines/Standards%20Addenda/135_1_2011_m_Published.pdf), section 13.8.1.1, describes a complete backup procedure that enters backup state using ReinitializeDevice STARTBACKUP, reads configuration files, and exits using ENDBACKUP. It therefore includes device-control requests. This service intentionally reads existing files without performing that procedure and does not claim an atomic/coherent backup.

JCI's [Transfer to Computer procedure](https://docs.johnsoncontrols.com/bas/r/Metasys/en-US/Controller-Tool-Help/15.0/Transfer-Operations/Transfer-Operations-Steps/Transferring-to-a-Computer) provides the genuine CAF upload workflow in CCT, including a BACnet/IP-to-MS/TP router option with explicit router address/port, trunk network and host interface. Its [troubleshooting documentation](https://docs.johnsoncontrols.com/bas/r/Metasys/en-US/Controller-Tool-Help/15.0/Troubleshooting/Tool-Functionality) identifies generated MOI/MOZ files and persistent-storage conversion as parts of native transfer. Copying arbitrary bytes from a File object does not replace that processing.

The authorized private seven-CAF corpus contains ZIP/XML authoring objects and no File-class records, native firmware upload decoder or embedded controller-package/compiler assemblies. The public OCT [reflection inventory](https://github.com/thecontrolscompany/oct/blob/c1d76ba7d6a8f17ca089c4671fa3333e4eba43e2/tools/dll-inspection-output.txt) identifies `Metasys.FCAccess` synchronization `CafFile`, `Upload` and `UploadAgent`, and `CafFile.ConvertToBinary`. Those are symbol/signature observations, not implementations or documented upload-session contracts.

## Service contract

`BacnetFiles(bacnet, store, timeout=3, operation_timeout=120, request_gap=0.05)` shares the already connected engineering interface. Each network operation holds that connector's lock and checks the exact application object, connection configuration and unicast target before and after each request.

- `inspect_config(address, device)` reads the specified Device's identity, vendor/model/firmware, maximum accepted APDU and existing Configuration_Files entries. If that list is empty, it inspects the Device Object_List for actually advertised File objects, refusing inventories above 512 objects or 16 Files. It reads each listed File's identity, name, optional description, file type/access method, size, read-only flag, modification timestamp, and record count where applicable. It returns an eight-session bounded inspection identifier and each File's exact metadata hash. `configuration_files` always retains the native list unchanged; `discovery_source`, `advertised_files`, `object_list_count` and `object_list_sha256` identify fallback evidence separately. No File identifier is guessed, and an inventory without Files is valid.
- `read_raw_file(inspection_id, object_id, metadata_sha256)` requires a matching readable File from that inspection and the same application/configuration. Device identity, configuration-file membership and complete File metadata must match before and after retrieval. EOF, exact original size and record count must agree. A changed or incomplete file fails visibly and is not saved as a complete capture.
- `captures()` lists saved evidence. `capture(id)` returns a verified receipt. `export(id)` returns bytes, filename and media type. Stream-access data exports unchanged as `.bin`. Record-access data exports as a ZIP with a receipt and one binary member per record, preserving boundaries and empty records; it is a local evidence container, not a proprietary native controller format.

Native metadata uses `file_access_method` values `stream-access` or `record-access`. A receipt includes original metadata, source/target/configuration, timestamps, byte count, SHA-256, pages, record boundaries and `native_caf: false`. Stable metadata is useful evidence but cannot prove that a running device left all file contents unchanged during the read.

The Object List fallback reads the native array count first. It reads a whole array in one request only when the count is at most 85 and its conservative encoded size fits both known APDU capacities; otherwise it reads the bounded entries sequentially. Returned array length, final count, object identifiers and uniqueness must agree. The full ordered inventory hash and advertised File identifiers are checked again after inspection and before/after capture. These checks avoid interpreting an empty Configuration_Files list as an absence of all File objects, while never relabeling arbitrary advertised files as standardized configuration backups. A large supervisory-device inventory fails visibly rather than automatically issuing thousands of indexed reads.

Only ReadProperty and AtomicReadFile are sent. ReinitializeDevice, ConfirmedPrivateTransfer, AtomicWriteFile, WriteProperty, discovery broadcasts and automatic connection changes are absent. Reads are sequential and throttled. Per-request timeout is at most six seconds; the whole network operation, including connector-lock wait, is at most 120 seconds. Maximums are 16 configuration files, 2 MiB per file, 4,096 records and 8,192 pages. Stream chunk sizes use known local/remote APDU capacity with conservative overhead; a record that exceeds this unsegmented result profile fails visibly. These bounds can stop a large file before completion; they do not promise every 2 MiB target can finish over MS/TP within the deadline.

Confirmed requests use the shared owned-dispatch exchange. Cancellation, timeout
and interface shutdown retire both the exact client transaction and its pending
dispatch, including the period before the native state machine assigns its own
invoke-ID field. A cancelled cache lookup cannot later send a metadata/file
request. The explicit disconnect API waits behind the file-operation lock;
lifecycle closure also cancels dispatch safely.

Captures live under `store.directory/bacnet-files`, outside source-controlled examples. Saving uses an exclusive bounded storage lock, temporary files, fsync and atomic no-overwrite linking. The profile retains at most 32 captures/32 MiB, rejects capacity overflow without deleting evidence, and rejects symlink/FIFO capture and lock files. Receipts and data have separate SHA-256 checks, with strict record-boundary and JSON resource checks. Hashes detect corruption; they are not manufacturer signatures.

## Connections workspace

The Advertised controller files panel uses the existing interface and an explicit address and Device object identifier. Inspect advertised files retrieves metadata only. Each advertised, supported File has a separate Read and save action; it requires the original inspection identifier and exact metadata SHA-256. The panel explicitly shows whether discovery used Configuration_Files or Object_List. A saved receipt records the controller identity, original file metadata, discovery evidence, connection configuration, transfer timestamps, content hash and consistency limit.

Saved captures and their receipts remain available with the interface closed and after restarting Studio. Export exact bytes verifies a stream's size and SHA-256 again in the browser. Record exports are ZIP evidence containers with individual record members and the complete receipt; the source-data SHA-256 covers the concatenated record bytes, not the ZIP wrapper. Receipt JSON can also be downloaded separately. Changing the parent target/interface or leaving Connections invalidates delayed results/downloads; a single-operation guard prevents duplicate clicks. Changing interface settings never automatically opens or reconnects an interface from this panel.

HTTP routes are `GET /api/bacnet/files/status`, `POST /inspect {address, device}`, `POST /read {inspection_id, object_id, metadata_sha256}`, `GET /captures`, `GET /captures/{id}` and `GET /captures/{id}/export`, with the abbreviated routes relative to `/api/bacnet/files`. Inspect/read require the local session token and normal origin/host guards. Export and receipt access only read verified local captures.

## Verification and missing native dependencies

Local tests pass through actual UDP exchanges with an independently authored File peer using the pinned BACpypes3 codec. They verify raw stream bytes, multiple/empty records, metadata/firmware/membership guards, Object List fallback with whole-array/indexed paths and malformed/oversized/duplicate inventories, APDU chunk bounds, malformed positions/counts/EOF, timeout/cancellation transaction cleanup, connector-lock deadlines, no write/control services, empty inventories, storage capacity, no overwrite, corruption and nonregular-file refusal. These tests establish the standard read implementation, not compatibility with every JCI firmware or native CAF recovery.

Two additional HTTP integration tests use the same actual UDP peer to verify session/origin/host guards, explicit opening, inspected metadata guards, stream/record exports, changed-file refusal and saved evidence after an offline restart. Browser coverage exercises the entire inspection/read/save/export workflow over real UDP, including empty records and offline receipt reopening, plus delayed inspection/download invalidation. All traffic in this verification goes to loopback test peers.

A genuine editable CAF upload still needs a matching authorized CCT/PCT installation and its compatible controller package/release database, with the native upload/persistent-storage conversion implementation (`Metasys.FCAccess.dll`/`Metasys.DataAccess.dll` and their installed configuration/definitions), or an independently verified replacement for those interfaces. No such installed bridge or public complete decoder was established. An actual vendor upload/reopen comparison and controller-specific acceptance evidence remain required. No proprietary service number, File OID or conversion rule is invented here.
