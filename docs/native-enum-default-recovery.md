# Previous effective Enum code recovery

In **Program → Native backup defaults**, inspect a retained current backup and
open an actual class 528/529 Enum default under **Merge retained saved settings**.
Open the matching original **Native Enum code transfer** receipt in the existing
transfer panel and choose **Prepare previous Enum default**. Preparation uses
retained evidence locally; it opens no interface and queries no controller.
Read a current backup first when connected. A retained snapshot does not establish
the controller's present state.

The profile is `native-enum-default-recovery-draft/1`. Its original receipt must
be resolved, show possible dispatch, and contain an immutable verified result or
verified readback event for `native-effective-enum-default-transfer/1`.
The recorded edit, unchanged Device identity, original backup and reconstructed
expanded native payload must agree. Older receipts without an explicit encoded
state-metadata fingerprint cannot qualify. A parent receipt is provenance, not
permission to replay its consumed transfer.

The current source must have the same exact route, vendor 5 identity, expanded
application and static directory as the recorded outcome. The selected record,
actual fixed saved Enum slot and encoded state metadata must match. Other
current saved values remain current. Codes are strict unsigned16 integers;
code meanings and allowed-state membership remain unverified. A third unrelated
current code, an unresolved original attempt, changed source or missing proof
refuses preparation. If the current code already equals the previous code,
preparation reports that fact and creates no transfer proposal.

The sealed origin records the parent intent and verified proof, original/current
backup hashes, class/reference/property, numeric previous/after/current/proposed
codes, actual four encoding byte sequences, state-metadata fingerprint and
captured storage. Equal numeric codes can have different encodings: a previous
one-byte zero can require a two-byte recovery encoding because the current
archive retains its width. The interface checks typed codes and each actual
encoding; it does not invent a single canonical byte sequence for an Enum code.

A prepared proposal appears beside the current Enum editor, receives keyboard
focus and exports the exact preparation response JSON. The ordinary raw draft,
including invalid text, stays separate. Discarding the recovery proposal restores
that text. Source-owned bounded workspace retention preserves local work across
navigation; it restores no review token or confirmations. Local compiled copies
remain separate from field operations.

Applying the proposal requires a **new Review controller default transfer**, the
exact controller/code/meaning confirmation, and the separate application-transfer
and interruption confirmation. Paired parent/origin hashes are reconstructed
before connected review and again before durable intent. Fresh application,
selected code/state metadata and directory must still match. Other fresh saved
settings are merged into the final payload. The existing ownership, credentials,
capacity, omitted-field qualification, one-use intent, one restore and full native
and effective readback remain required. The child receipt binds its review
snapshot and recovery origin independently of the final fresh payload.

Edits, target/source changes, navigation, Stop and page lifecycle changes retire
reviews and late preparation/review replies. A response to an already dispatched
operation can still retain its uncertain receipt. Lost acknowledgements or failed
verification block another write and retain readback/restart reconciliation
without replay. No automatic inverse, whole-backup restore or batch transaction
is introduced. Structured recovery lineage in the common Changes view is a
separate follow-up; exact native receipt evidence remains available here.

The token-admitted preparation endpoint is `POST
/api/bacnet/controller/native-application/enum-default/recovery/prepare` with
only `receipt_id`, `capture_id` and `snapshot_sha256`. The existing Enum transfer
preview accepts the paired optional `recovery_parent_receipt` and
`recovery_origin_sha256`. Apply still accepts only its reviewed one-use token and
existing strict confirmations. Native application status reports this recovery
profile separately from transfer support.

Qualification uses literal class 528/529 plain/gzip sources and isolated authored
direct/routed UDP peers. It covers strict evidence/type checks, zero-width
differences, current unrelated saved values, already-previous and third-code
outcomes, altered originals/metadata, unresolved/reconciled parent attempts,
fresh pre-intent rejection, one-use transfer and uncertain restart reconciliation.
Chromium/WebKit checks cover offline/CAF entry, phone/focus, exact response export,
raw draft restoration, source/navigation/lifecycle retirement, new confirmations,
fresh field transfer and lost-acknowledgement readback. Software evidence does
not establish CCT reopening, a manufacturer compiler oracle, Enum semantics or
physical controller acceptance. No site, VM or Bluetooth test is part of this
qualification. A removed selected saved slot or changed static directory requires
separate engineering; this profile does not infer historical capacity from a
model name. General native programming remains partial.
