# Owned confirmed-service response lifetime

`confirmed_exchange` creates a private response future bound to the running event loop. Its first result, exception or cancellation remains authoritative. Further native result/exception completions during the same cleanup window are ignored only for that owned future. Pending completion delegates to the standard `asyncio.Future` implementation. SDK-created futures retain their ordinary strict setters.

The pinned BACpypes3 0.0.110 `Application.confirmation` finds the peer/invoke registration and calls `future.set_result` or `future.set_exception` without a done-state check. Request removal runs in a scheduled future callback and the owned exchange's `finally`. A native reply can reach that registration after cancellation but before removal, causing `InvalidStateError`; a duplicate completion has the same window. The private future closes this completion race without replacing SDK handlers, global hooks, event-loop behavior or the existing request/transaction retirement rules.

This is the lifecycle portion of `COMM-008`. It changes no source/service/invoke validation, response or operation timeout, retries, dispatch count, read evidence or command uncertainty policy. A cancelled request stays cancelled. A reply that missed its deadline does not become an accepted historical result, and a failed initial read does not acquire a continuation cursor. Interface closure and cancellation before native preparation completes still retire owned work; they do not schedule detached sends.

`tests/test_owned_response_future.py` uses actual loopback UDP replies and a controlled per-test application boundary to expose the native completion-before-cleanup window for ACKs and errors. A held unrelated SDK request survives owned cleanup and completes normally. Separate checks preserve first results/errors/cancellation across opposite later completions, bind the future to the active loop, close the interface at reply delivery, and cancel native preparation without a subsequent send. No building controller, Bluetooth adapter or physical interface is involved.

The original frozen18 full-suite read timeout and its later native `InvalidStateError` remain preserved separately. These regressions establish the completion-race fix; they do not establish why that original reply missed its deadline or repair its incomplete report.
