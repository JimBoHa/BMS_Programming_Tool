# Owned local simulation session retirement

The Program simulator's in-memory calculation cache remains bounded at 25 sessions with a one-hour idle expiry. Resetting or replacing a graph now explicitly retires its exact known calculation session instead of leaving every old engine cached until expiry. This does not raise the limit or clear unrelated sessions.

Each successful step receipt supplies a random retirement token and immutable creation-operation identity. The browser retains this handle in memory, verifies the current operation/source/count/timestep and known ownership, and sends the exact handle to `POST /api/simulation/retire`. The server compares token and original creation identity before removing that one engine. Repeating a verified retirement after the engine is absent succeeds idempotently. These tokens are not serialized into projects, browser recovery drafts or recorded trend exports.

Known handles are detached immediately on Reset, source replacement, successful independent scenario completion, actual React unmount and non-BFcache page hide. BFcache page hides preserve the live document's known session. A first step response arriving after reset, source replacement, page hide or unmount is still checked against its exact admitted operation, source/count fields and ownership proof before its newly disclosed handle is retired. It cannot revive the editor or nominate an unrelated session for removal.

Run, Step and scenario admission wait for outstanding cleanup. Unconfirmed cleanup appears separately from scan and recording errors; **Retry session cleanup** retries failed owned handles within the current document. No scans are retried automatically. The cache-status button retrieves a local count/limit/expiry snapshot; it does not enumerate, change or clear other sessions.

Before the first asynchronous retirement handoff, the browser records only that already-requested deletion intent in same-origin, per-tab `sessionStorage`. Active sessions and unknown IDs are never added. The record holds at most32 exact session/token/creation-operation handles and16KiB of text. A matching validated retirement acknowledgement removes only its exact handle; ownership collisions, malformed records and capacity pressure do not overwrite or evict retained records.

After reload, one authenticated document attempts each retained idempotent local retirement once before admitting new calculation work. Failure still requires explicit Retry within that document. This completes previously requested cleanup; it does not execute or retry scans, field writes or controller actions. Waiting for initial authentication prevents an unauthenticated bootstrap attempt. Unavailable or corrupt browser storage is reported while known in-memory cleanup is still attempted; no unknown ID is guessed. Per-tab storage survives reloads but does not guarantee recovery after the tab itself closes.

Retirement cannot roll back a batch already admitted. The current server executes a batch synchronously without yielding; retirement occurs before or after that batch. A retired calculation's durable trends, alarms, events and source lifecycle remain unchanged, including active/unacknowledged alarms. Ending or retiring an observation source remains a separate explicit workflow. An independent scenario failure preserves the known main calculation; a successful scenario replaces its displayed trace and releases that old calculation.

Lifecycle requests use best-effort fetch keepalive, with the bounded pending-intent record supporting a later reload when its acknowledgement is lost. Document termination, browser/storage/network limits and missing or unverifiable first responses can still prevent cleanup. An unknown handle is never guessed or globally cleared; its engine may remain until idle expiry and still counts toward the 25-session limit. The UI explains this uncertainty. Explicit reset creates a new calculation only after known cleanup completes; it does not assert that an unknown old request executed zero scans. The feature affects local portable graph calculations only, with no field interfaces or native controller changes.

Verification includes more than 40 reset/source cycles and real reloads while a separate retained session remains stable, delayed first replies after reset/source change/page hide/actual React unmount, pending cleanup admission gates, wrong ownership/creation identities, explicit retry after a lost cleanup receipt, BFcache retention and unchanged durable recorded history/active alarm/source data. Deterministic lost-retirement cases fail against the earlier installed artifact; reload recovery covers Reset, page hide and delayed initial authentication. Storage checks exercise exact acknowledgement, conflicting capabilities, malformed records and bounded no-eviction behavior. Fixtures retire only IDs/proofs from their own actual receipts through the public API. Backend tests separately cover ownership/auth/expiry guards, legacy callers, repeated retirement and durable evidence after restart.
