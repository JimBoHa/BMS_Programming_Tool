# Recover a previous native point name

In **Points & I/O → Configuration → Edit point name**, select a retained point-name
transfer and obtain a current point-name backup. Open **Previous point name** and
choose **Prepare previous point name**. Preparation reads retained evidence only;
it does not query the controller or replay the earlier operation.

The proposal shows the original previous name and the name in the selected current
capture. **Use previous point name** stages the proposal while retaining the
operator's ordinary name text separately. **Return to saved point name draft**
restores that exact text. Task navigation retains both within the existing
32-context point-name work capacity. A fresh capture or receipt selection retires
the prepared proposal and preserves the ordinary text. Editing the staged name
retires its recovery binding; it cannot silently retain the old review.

Choose **Review point name change**, review the exact selected point and native
transfer effects, confirm the name and application transfer, then **Apply point
name**. The new operation retains the existing Device identity, point identifier,
reference, wiring, I/O setup, fresh other saved settings and complete native
readback requirements. Successful owned completion restores the ordinary text;
an older retained receipt cannot clear newer source work.

## Evidence required

The separate `native-point-name-recovery-draft/1` profile requires a resolved,
confirmed native point-name transfer with possible dispatch and an immutable
verified result or verified historical readback. An unresolved attempt must be
reconciled first. Preparation reconstructs the original compiled payload from its
original backup and typed edit, checks its complete compilation/hash evidence,
then independently qualifies the current retained source.

Device identity and route, the static saved-parameter directory, point identifier
and native reference remain exact. The current point name must equal the recorded
before or after name. Normalizing only that name must yield the original verified
after-image; unrelated native application changes refuse. Other current saved
values stay current and are merged by the regular compiler. Current encoding,
name collision and ordinary typed-name restrictions remain enforced. Unsupported
or invalid historical names are refused, never silently corrected.

A captured point already at its previous name has no proposed change. This
describes the selected capture, not a fresh observation of the physical device.
**Save previous point name proposal** preserves the exact original response bytes;
it exports evidence, not an executable transfer plan or automatic rollback.

The local token-admitted endpoint is
`POST /api/bacnet/controller/native-application/point-name/recovery/prepare`, with
`receipt_id`, `capture_id` and `snapshot_sha256`. It declares `read_only: true`,
`controller_queries: false`, `field_actions: false` and `can_apply: false`.
The backend supports preparation without an open interface. The selected-point
web workflow uses its retained/captured context; opening a new field context or
loading a reference file does not independently establish controller acceptance.

## New transfer and uncertainty

The existing point-name preview accepts the paired optional
`recovery_parent_receipt` and `recovery_origin_sha256`. Both must match a newly
reconstructed proposal and its exact current source/edit. The regular point-name
Apply requires both explicit confirmations and a fresh one-use review. It checks
the original recovery proof again before retaining the new durable intent. The
new receipt carries its exact recovery origin separately from the unchanged
parent receipt; ordinary point-name changes remain ordinary.

Fresh selected identity, published prior name, native application/static-directory
hashes, reported capacity, saved settings, credentials and interface ownership
continue to govern dispatch. A possibly dispatched attempt remains uncertain
until explicit complete readback. Reconciliation retains its original result and
origin and sends no replacement application. It never reuses an old plan or
automatically attempts an inverse operation.

Navigation, source/receipt selection, editing, visibility and page hiding retire
pending reviews and late preparation responses. Browser checks bind the parent
proof, current capture, point/ref/name and exact recovery origin before displaying
a proposal or accepting its new review/receipt. Local preparation does not lock
the rest of the workspace as a field mutation.

## Software qualification and remaining scope

Authored tests exercise compressed/plain originals, supported character encodings,
changed source/identity/route/static data, malformed/unverified/pending parents,
fresh other settings, exact original receipt preservation, pre-dispatch proof
substitution, restart readback and uncertainty without replay. Actual direct and
routed loopback peers qualify the separately confirmed new transfer; captured
source/navigation fixtures qualify local-only UI behavior with the real backend
interface closed. Chromium/WebKit cover proposal/draft preservation, both entry
paths, exact evidence downloads, retired/substituted replies and compact layout.

Physical acceptance, Bluetooth, general application rollback, hardware reassignment
and whole-state migration remain separate. Recorded point-name rows continue to
show their existing metadata; a dedicated searchable projection of point-name
recovery lineage remains a separate Changes/History extension.
