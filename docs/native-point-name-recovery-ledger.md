# Recorded point-name recovery lineage

**Changes** and **History → Recorded changes** now identify the recorded parent
of a previous-point-name transfer. Select a native point-name row to see the
point identifier/reference, unchanged Device instance, recorded prior name,
requested previous name and historical parent-verification reference. The
ordinary row outcome/readback remains separate from this recorded proposal.

**Search recorded point-name parent receipt** searches local native records by
that exact recorded ID. Results may include children referencing the ID. A
matching child does not prove that the parent receipt or original backups are
available. Search does not load a parent as recovery proof, select its historical
controller or create a transfer. The existing point-tools link continues to
require a current controller selection and does not adopt historical points,
routes, drafts or authority.

The pure `native-point-name-recovery-recorded/1` projection checks the known
origin schema/seal and child receipt's original point-name edit/compilation,
confirmation, point/ref/name/encoding, review-capture and Device bindings. Local
hashes detect changed recorded evidence; they do not authenticate a manufacturer
or establish present source availability. The browser independently checks the
flat metadata profile, exact point/Device/name bindings, ID/hash bounds and typed
historical verification before displaying the lineage or enabling parent search.

Missing, unknown or inconsistent origin metadata stays unavailable; the original
receipt JSON remains readable and its download retains exact endpoint bytes.
Ordinary point-name records retain their existing projection. Generic
Real/Boolean/wire/controller-name/instance lineage readers remain unchanged.
Original intents, results, events and capture files are never rewritten.

Recorded bindings can be displayed when referenced parents or native files do
not resolve. The reader does not call the local recovery preparer, verify a parent
readback, reopen original native files, connect an interface or contact a
controller. A future recovery still needs its separately qualified original
evidence, fresh source, explicit review/confirmations, one-use transfer and full
readback. Recorded metadata supplies no part of that authority.

Software checks include a real authored recovery transfer followed by restart
and query/HTTP/export with field/original/parent-revalidation methods forbidden;
unresolved recorded references; malformed bindings and immutable original
receipts. Chromium/WebKit cover both local entry paths, Changes/History,
parent search, exact downloads, unavailable/substituted metadata, late-response
retirement and phone layout. Physical controllers and Bluetooth are not qualified
by this local recorded-evidence feature.
