# Previous native execution-order proposal

`COMM-NATIVE-ORDER-PREVIOUS-PROPOSAL-001` adds local previous-order assistance to
the existing native execution-order receipt and retained-result comparison.
It uses the actual qualified order compiler; it does not reverse a displayed
list or replay the original transfer.

## Workflow

1. In **Program → Native backup defaults**, open a retained native source and
   inspect the original receipt's diagram using **Execution order**.
2. Choose the controller destination, load the original order transfer receipt,
   then compare its recorded result with the selected retained source.
3. Expand **Prepare previous execution order** and prepare the proposal. The
   recorded after application, effective order and static saved directory must
   all match. A difference disables assistance; it does not justify a guessed
   rollback or establish an already-restored condition.
4. Inspect original/current order members, local compilation and immutable origin
   evidence. **Save exact previous-order proposal** saves the original HTTP JSON
   bytes. Preparation and export preserve the existing unfinished order draft.
5. **Replace local order proposal with previous order** explicitly loads the
   guarded original permutation into the existing local editor. Replacing a
   different unfinished draft requires confirmation. No controller changes.
6. Use the existing local review/export controls to produce a native file copy.
   The separate [previous-order controller transfer](native-order-recovery-transfer.md)
   can select the verified previous order without replacing this draft. It
   requires its own fresh confirmed review, transfer and complete readback. This feature
   records no field recovery lineage and supplies no field authorization.

An open interface or historical verified result never establishes current
controller state. The proposal remains useful offline, including from a CAF
workspace. Original files, graph/CAF drafts, receipts and journals are retained.
Cancelling, changing source/receipt/draft/target/mode/task/workspace, closing the
disclosure or leaving the page retires pending and completed proposal exports.

## Evidence and compilation

The existing result comparison reconstructs the original payload from its actual
File3/11/12 capture, original configuration guard and immutable verified result
or first verified readback. A later unknown observation does not erase that
historical proof. Recovery-parent receipts and inconsistent or unresolved evidence
are refused by that original comparison profile.

Preparation additionally requires the original static directory and a matching
retained expanded/effective application, identity, exact route, membership,
recorded permutation, payload widths and wire relationships. The original
pre-transfer permutation comes from the validated original intent. The ordinary
saved-effective compiler applies it to the selected current captured source and
independently checks native structure and every other merged byte. Source
encoding may differ when the expanded application is equivalent; the existing
compiler preserves the current original wrapper/header.

The sealed JSON binds the original intent and selected immutable proof, original
backup/snapshot, current comparison, exact proposed request and complete local
preview. Browser admission independently validates the source, original proof,
permutation, byte-patch/phase/width evidence and nested compilation seals. Loading
the draft rechecks that report and the editor's current source/lifetime before
using its existing guarded draft cache. Internal hashes establish consistency,
not vendor authentication or present physical controller acceptance.

## Limits and qualification

The profile deliberately refuses changed current saved values, changed static
directories or other native edits that prevent an exact recorded-after match.
It does not restore arbitrary snapshots, release overrides, reassign hardware,
allocate new objects, migrate packages or provide a general JCI compiler.
Firmware runtime/CCT equivalence, physical commissioning and BTCVT acceptance
remain separate. The separate [previous-order controller transfer](native-order-recovery-transfer.md)
now records typed lineage through its own profile; an ordinary new order transfer
is not retrospectively labelled as recovery.

Authored localhost peers exercise both supported diagram classes, raw/gzip
sources, immutable verified readback, altered proofs/guards, mismatched route or
saved values and missing originals. Independent parameter application to the
original before image checks the complete inverse native data. Tests assert no
new field events, plans, capture folders or receipt mutations. Browser checks
exercise CAF/new-graph and compact/desktop paths, exact evidence and compiled-file
exports, draft confirmation, forged responses, navigation/lifetime retirement,
and the existing order editor and transfer workflows. These are software checks,
not physical acceptance.

The initial **Native order qualification** GitHub Actions workflow qualified the scoped
cohort against a clean, immutable commit in source and installed-wheel form, with
Chromium and WebKit in the repository's pinned Playwright container. It declares
326 backend cases per build and 425 browser/contract cases per matrix: 2,352
executions in total. Collection identifiers must match executed identifiers;
failures, errors, skips, retries and missing cases fail qualification. Each group
keeps its logs, original collection/results JSON and failure traces as artifacts.
Installed checks verify exact tracked Python, UI assets/build provenance, public
metadata, reference data and legal files before using the wheel's package and UI.
Six additional connection-prefill regression cases per matrix precede that
unchanged cohort, for 2,376 total executions. They cover a queued automatic
network recommendation or saved-status hydration reaching an already focused
bind-address draft, including desktop and compact selection/text replacement.
Focus preserves the displayed complete connection draft synchronously, so an
automatic prefill queued earlier cannot later replace it or move its insertion
point. Untouched drafts still receive recommendations and saved settings. The
large-order capability case observes its actual analysis response before testing
the rendered report; its existing case/assertion budgets and assertions remain.

To run a matrix locally after building the UI and installing the locked runtime,
build tools, pytest and pinned Playwright browsers, use a fresh ignored output
directory from a clean committed checkout:

```sh
PYTHONPATH=backend:. .venv/bin/python scripts/qualify_native_order.py \
  --mode installed --browser chromium \
  --output release-output/native-order-installed-chromium
```

Repeat with `source` and `webkit` for the other matrix combinations. Backend
checks run in each build's Chromium job, once per build. Running these authored
software checks on Linux does not establish macOS desktop-session health or
physical controller acceptance.

The separate previous-order transfer expands the same immutable cohort to 417
backend cases and 480 browser/contract cases, plus the six prefill cases per
matrix. See [its qualification scope](native-order-recovery-transfer.md).
