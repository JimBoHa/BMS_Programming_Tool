# Draft recovery across fast reloads

The editor keeps its existing 200 ms validation/autosave debounce. In addition, page hide, before-unload, hidden-page and React unmount lifecycle handlers synchronously serialize the latest ready editor snapshot into browser storage. A reload immediately after editing or saving no longer depends on the debounce timer firing first. Startup handlers do not write the initial placeholder before project recovery has finished. A startup storage-read, JSON-parse or unsupported-shape failure disables every automatic recovery write for that page, including macro transitions. The existing raw copy is preserved, an explicit recovery-unavailable message remains visible, and editing, server saves, import/export and validation stay usable. Restoring storage access or making another edit does not silently re-enable writes; reload retries recovery.

`web/src/draftRecovery.ts` exports `persistDraftRecovery(storage, program, macroEdit)`. A normal snapshot writes the existing `bms-studio-draft-v1` key, then removes stale `bms-studio-macro-edit-v1` recovery only after the normal write succeeds. A macro snapshot writes `{parent, definition, draft: program}` to the macro key and leaves the parent recovery intact. Entering macro edit, debounced persistence and lifecycle flushes share this serializer. Apply/discard first writes the updated/restored parent, then clears macro recovery. Program and macro references are updated synchronously, including functional macro-parent updates after a revision save, so lifecycle events see current data rather than a captured earlier render.

Storage/serialization failures are shown separately from graph validation and do not stop the validation request. A failed primary write does not clear a previous macro copy. The two keys are not one storage transaction: if stale-macro removal fails after a successful normal write, both copies remain, the failure is visible, and startup still gives a valid macro copy precedence. Save a server revision or export current work when browser recovery reports a failure.

Browser storage and lifecycle handlers are recovery aids, not durable project backups. Browsers may omit unload events during a process crash or forced termination, storage can be cleared or denied, and a successful storage API call does not certify disk durability. Normal revision save/export remains available. This change does not alter graph schemas, saved revisions, native evidence, controller programs or field interfaces.

Verification holds the 200 ms timer deterministically while reloading ordinary and macro drafts, applying/discarding definitions, changing the latest source and firing each lifecycle event. Tests cover initialization/read/parse guards, actual React unmount, serializer ordering/failures and validation continuing after storage failure. Chromium and WebKit also run the unchanged equipment-wizard save/export/reload workflow that exposed the original race.
