# Previous effective native Boolean default

Profile `native-boolean-default-recovery-draft/1` prepares the previous effective
value of one existing class-530/531 property-3113 Boolean default from an original,
historically verified native Boolean-default transfer receipt. It requires a new
confirmed transfer and full readback. General JCI-10 restore remains partial.

## Operator workflow

1. Open **Program → Native backup defaults** and select a retained source. When
   connected, explicitly **Read current native backup** first; capture enters and
   ends backup mode. Open **Inspect retained native backup** and inspect the
   original Boolean field named in the receipt.
2. Choose **Boolean default source → Merge retained saved settings** and **Open
   saved Boolean defaults**. Archive and effective values remain separate. Open
   the original Boolean transfer receipt in that field's transfer section.
3. Resolve a pending original attempt through explicit readback before another
   edit. **Prepare previous Boolean default** reads only retained local evidence.
   A different selected Boolean field keeps preparation unavailable and identifies
   the original field to open. Local preparation works without an open controller.
4. Focus moves to the prepared result. The proposed checkbox is locked while the
   recovery proposal is active. **Discard previous Boolean proposal** restores the
   separately retained ordinary draft. Source/field-bound proposals survive task
   navigation; exact JSON exports preserve their original response bytes. These
   are bounded transient browser drafts, not a new persistent project format.
5. If the retained source already has the previous value, no transfer proposal is
   created. The source remains historical and does not establish current live
   state. Otherwise choose **Review controller default transfer**, inspect the
   actual route, field, Boolean values/tags and parent receipt, and confirm both
   the edit and controller interruption before Apply.

Field transfer requires the existing qualified direct or explicitly routed plain
IPv4 native adapter, matching controller/source/interface, private credentials and
zero owned commands. It consumes a new one-use review. The old token and payload
are never replayed. Source, field, value, target, interface, task visibility and receipt
changes retire pending responses/reviews, including A-to-B-to-A transitions.

## Evidence and preservation

- A separate Boolean-default receipt must retain a possible dispatch, no pending
  uncertainty and an immutable verified result or historical verified readback.
  An explicit no-dispatch result cannot gain recovery authority from readback.
- Original backup integrity, native identity, saved schema, compiled payload and
  selected class/reference/value/tag must agree. Native Boolean tags are exactly
  `10`/`11`; values are actual `false`/`true`. Numeric `0`/`1` aliases and invalid
  saved encodings do not qualify.
- The current retained source must have the same route, Device and identity, the
  recorded original-after expanded File 3 and original static parameter directory.
  Container recompression can differ while the expanded bytes remain identical.
  Changed application/configuration and unknown saved formats require separate
  engineering. Other current saved settings stay current.
- New review and pre-intent Apply reconstruct the parent/proof/source lineage.
  Apply captures a fresh source, refuses a changed selected value, application or
  directory, merges other fresh saved settings and checks actual File-3 capacity.
  Existing ownership, credentials, cancellation, expiry and uncertainty guards
  remain. The child intent records `recovery_origin` and its hash; the parent and
  original dispatch/result are unchanged.
- One existing File-3 restore can interrupt control. Verification requires the
  complete native image, identity, operational state and effective-setting
  preservation. A lost acknowledgement remains uncertain; explicit readback can
  resolve it after restart without another restore. No automatic inverse write
  or retry occurs.

The existing 900-second review, 1,800-second operation budget, four-second
individual File request bounds and native storage-preparation interval remain.
Capture/readback can send start/end-backup state commands. No new transport,
block/link/I/O allocation, whole-device restore or physical acceptance is added.

## API and recorded Changes

`POST /api/bacnet/controller/native-application/boolean-default/recovery/prepare`
requires the local session token and `receipt_id`, `capture_id` and
`snapshot_sha256`. It creates no field query, plan or transfer intent. Pass its
proposal with the returned `origin_sha256` as `recovery_origin_sha256` to a new
Boolean `/transfer/preview`; the paired `recovery_parent_receipt` is required.
The server reconstructs the origin and requires the exact previous Boolean.

Changes projects only this known Boolean origin profile with strict values/tags
and child-receipt bindings. It labels Boolean values separately from Real bits,
retains original dispatch versus later readback and supports the same bounded
local parent-ID search. Listing does not revalidate parent/source files or
authorize another recovery. Unknown or malformed metadata stays unavailable;
original receipt downloads remain readable.

Qualification uses authored byte/schema cases, strict local HTTP, direct/routed
UDP native peers and Chromium/WebKit workflows. Physical controller/RS-485/BTCVT
and equipment behavior acceptance remain separate. Real, Boolean, wire, name,
instance and general recovery retain distinct contracts.
