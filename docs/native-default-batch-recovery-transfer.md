# Deploy previous effective typed batch values

Open **Program → Native backup defaults**, select the retained current source and
load the original verified batch receipt. **Prepare previous batch defaults**
derives its prior effective values locally. Expand **Transfer previous batch
values to controller**, then choose **Review previous batch recovery transfer**.
Review the exact target and values, confirm the defaults and possible control
interruption, then **Apply previous batch values to controller**.

Opening recovery retires an ordinary batch review while preserving its unfinished
draft. Recovery and ordinary transfers share the existing operation ownership
lock. Coalesced task changes retire handlers before dispatch. A callback retained
after a review was consumed cannot send that review again. Field capture/Apply/
readback keep their original timing, credentials, limits and uncertainty rules.

## Fresh reconstruction and preservation

The original verified receipt and original/current retained files are reconstructed
before preview and again before durable intent. The proposed request must equal
the locally derived prior values and origin hash. The selected typed guard must
remain unchanged. No caller-supplied origin object, old token or old payload
authorizes another operation.

Apply captures fresh actual Files3/11/12. Application and saved directory must
match the reviewed source; selected values, encodings, types and Enum storage/
state metadata remain guarded. Other fresh saved settings are merged into the
final payload. One durable File3 restore changes up to sixteen originally selected
Real/Boolean/Enum defaults. Complete native application and every selected
effective value must read back correctly. Float32 signed zero and strict Boolean/
numeric Enum values retain their existing qualification. Enum meanings and set
membership remain unverified.

The new intent retains its parent receipt/intent/proof, original/current capture
bindings and exact origin seal. The parent is unchanged. Missing or contradictory
original evidence before intent refuses recovery without another restore. Original
whole-image readback remains separate from verifying the proposed prior values.

## Uncertainty and retained records

A lost acknowledgement retains a durable uncertain receipt and blocks new
engineering writes. Load that receipt from **Retained default-batch receipts**;
recovery rows are labelled. Reopen its exact controller/interface and choose
**Read back previous batch recovery**. No preparation, old-token replay or second
restore is required. This works after browser reload and process restart.

Readback uses the child operation's own immutable intent/backup. It does not
require the original parent's files to remain available after dispatch. New
recovery preview/Apply still require their full original evidence. Read-only
receipt validation preserves historical verified readback after a later
inconclusive observation without claiming new current-device verification.

Exact receipt JSON remains downloadable. The ordinary Changes/History batch
projection explains that recovery lineage is not projected there; original
receipt details remain available. A searchable recorded recovery projection is
a separate follow-up.

## API and scope

The existing `/default-batch/transfer/preview` accepts the optional paired fields
`recovery_parent_receipt` and `recovery_origin_sha256`. They are either both absent
or both present and rederived by the server. Ordinary request/review/intent bodies
retain their earlier shape. Apply keeps its existing strict one-use token,
review hash and two confirmations.

Recovery adds `recovery_profile`, `recovery_scope`, `recovery_origin` and
`recovery_origin_sha256` to the independently sealed review and intent. The addon
profile is `native-default-batch-recovery-transfer/1`; the underlying typed batch
operation profile and compiler remain independent. Earlier browser field receipt
predicates remain unchanged; a separate strict recovery predicate validates these
annotations and the recorded typed values before using the existing preservation
checks. Captured identity, an open interface and current responding-device
verification remain separate states.

Qualification uses authored direct/routed BACnet peers and source/installed
Chromium/WebKit workflows. No site, Bluetooth or physical-controller actions are
needed. This is bounded previous-default recovery, not general application rollback,
new block/I/O allocation, package/resource/runtime/CCT comparison or physical
acceptance. JCI-03, JCI-09 and JCI-10 remain partial overall.
